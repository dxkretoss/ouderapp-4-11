- Device preferences live in src/lib/voorkeuren-store.ts (localStorage); legal resources are a config array in src/lib/juridische-bronnen.ts — so they can later come from admin/db.
- Menu categories are separate from the preserved shortcut defaults; help and child contact selectors stay sheets in /meer pointing to existing routes, so reorganizing navigation never copies family data or resets onboarding silently.
- Financial inputs reuse GeldInvoer and geld-invoer parsing; expenses retain optional budgetId for source-based coverage, never duplicate budgets or purchase ideas.
- Agenda presentation uses agenda-presentatie for week labels and source-derived response selection; proposal menus reuse existing flows and care cells preserve split surfaces under handover stripes, so layout cannot own planning or approvals.
- Payment shortcuts open Afrekenen; request descriptions reuse settlement wijze, bank inputs stay ephemeral, and request amounts cannot bypass settlement eligibility.
- VoorstellenOverzicht in Activities derives responses and reminders from existing sources; legacy Samen regelen redirects there — so navigation never owns a second proposal store.
- Plans, subscription status and data retention are config in src/lib/abonnement.ts; cancelling and deleting an account are separate flows — so pricing changes need no UI rewrite.
- Communication pressure and the message-pause rule are pure, configurable functions in `src/lib/communicatiedruk.ts` based only on objective signals, computed only for conversations the viewer may access — so the indicator stays explainable and never judges people.
- Holidays are computed per year in `src/lib/bijzondere-dagen.ts` (Easter algorithm, 25+ years ahead) and are display-only — so no yearly lists need maintenance and a holiday never alters care schedules.

- Budget proposals live in `src/lib/budget-store.ts` with an append-only step list and audit events; they never become a cost item until "Uitgave toevoegen" runs the existing cost flow — so a future expense is never treated as a payment.
- Budget postponement records a review timestamp in the existing step, never a deadline or scheduled delivery — so date selection cannot imply notifications without secure linked accounts.
- Solo email linking lives in src/lib/email-koppeling-store.ts: only messages from/to the one linked address pass filterVoorKoppeling, originals are frozen, suggestions never apply themselves, and linking grants no app access — so a mailbox can never leak into the app.
- Smart help reads stores, max 3, toggleable — no copies or unconfirmed changes.
- Living Home sfeer is pure regels in src/lib/living-home.ts plus a pointer-events-none layer (LivingSfeer) behind the Home top; weather uses one user-set place via Open-Meteo, no GPS — so dynamics never move or hide functional content.
- Private agenda items (gedeeld=false) stay in the one Agenda; overlap uses controleerPrive in src/lib/slimme-hulp.ts (only when the owner has a concrete task) and they are never logged to the shared audit — so private details never reach the other parent, exports or professionals.
- Extra houvast keeps `/extra-ondersteuning` and groups existing routes; `extraHouvast` in voorkeuren-store controls only optional presentation, never requests, rights or data. Device storage is not authenticated user persistence; Kretoss must connect this preference to the existing account settings.
- The agreements overview hides unchanged demo seeds through isIngevuldeAfspraak; source records, deep links and pending-request readers stay intact, so removing examples from presentation never deletes history.
- Afspraken tussen ouders hebben één bron: `src/lib/afspraken-store.ts` (versies, voorstellen, akkoord per ouder), getoond op `/afspraken`; `/afspraken-veiligheid` is alleen een doorverwijzing en ouderschapsplan-import schrijft direct in die bron — so there is never a second agreements list.
- audit-store starts empty (no seeded demo events); `/tijdlijn` and `/exporteren` read audit events plus afspraken-store geschiedenis directly, never copying agreement history into audit — so there is one history per source and no fake past.
- Home is one component (Dashboard in src/routes/index.tsx); when start-store `eigen` is set it swaps in EigenKinderen/EigenVandaag/EigenVolgende from EersteHome.tsx and drops demo-seeded sources (demo agenda, actions, costs, pro, the na-demo Nu afstemmen) — so Home improvements are made once and demo data never shows as real.
- Own-family agenda items live in start-store `agenda` (same device storage as the eigen children/regeling); the demo family keeps its own session-only list in agenda.tsx — so demo and own data never mix.
- Agenda edits apply directly for personal items, or in an own family while no other parent is invited (start-store uitgenodigd); otherwise shared edits stay proposals — so nobody waits on a parent who is not there.
- Own-family message topics live in start-store `onderwerpen` as drafts only; nothing is sent until a real linked parent exists, and demo gesprekken/demo replies never render for an own family — so no fake exchange.
- Own-family expenses and the provisional cost agreement live in start-store `kosten`/`kostenAfspraak` and reuse the NieuweUitgave form via an `eigen` prop; no saldo or payment request exists until a real second parent is linked — so demo costs never mix with own data.
- Meer sub-pages (taken, nog nodig, spullen, momentjes, documenten) wrap their demo component and show EigenLeeg for an own family; Kinderen and the kind profile read start-store kinderen (ids "k-…") — so demo data never shows as real.
- Own-family gezag is one self-reported value in start-store `gezag` (who filled it in, never confirmed by the other parent yet) and is display-only — so self-reported authority never grants access.
- Profile images (parent and own-family children) are one optional `beeld` field in start-store ("avatar:n" built-in SVG avatars, or a device-side cropped/re-encoded JPEG data URL), rendered only via `ProfielBeeld` — so no second profile store and no external avatar service.
- afstemming.ts derives topics/stalemates from existing zorg proposals (no own storage or status) — so no parallel proposal system.
- zorg-store owns versioned per-child schedules and exceptions; only accepted proposals change planning, final statuses are immutable — so nothing reverts silently.
- Change history (`src/lib/audit-store.ts`) is append-only structured events (frozen, no edit/delete); stores log centrally and timeline + PDF read the same events — so history can't be skipped or diverge.
- pro-journaal-store owns pro data; visibility defaults to none; parents use voorOudersVan, never internal notes. trekToegangIn keeps confirmed internal summary/end date on DossierPro; closed cards show only own summary, no family access or export — to avoid disclosure.
- Nog nodig reuses useLijst per family mode across navigation; cost/budget links prefill existing forms without creating expenses — so no duplicate purchases.
- Writing help uses coach-vergelijking plus AI meaningful-change signal; ephemeral coach-cache keys exact text/context/style, never a rewrite — so stale or cosmetic results cannot approve messages.
- Budget coverage of expenses is decided only by beoordeelKosten in src/lib/kosten-akkoord.ts (category, child, validity, period usage, duplicates; unknown → uncertain) — so an expense never uses budget twice or is auto-approved on a guess.
- Success toasts go through bevestig() with one fixed toast id; page confirmations are shortened by kortePopup() — so only one popup shows and 'Geregeld!' appears only for definitive confirmations.
- The cost overview limits presentation with kosten-overzicht.ts and opens existing cost/budget/history views; it never copies records or changes eligibility — so compact layouts preserve financial rules.
- Afrekenen uses the existing settlement history with linked cost IDs and guarded participant transitions; demo payment links stay session-only, bank details stay unavailable until authenticated shared storage exists — so declarations never prove receipt or duplicate settlements.
- Nog nodig items keep only an optional budgetId in their existing KleineLijst entry, explicitly linked by the parent; budget-weergave reads confirmed source amounts without creating expenses on completion — so practical and financial records never duplicate.
- Openstaande voorstellen: src/lib/openstaande-voorstellen.ts leidt één overzicht af uit zorg-/afspraken-/budget-/vakantie-/kosten-/aanwezigheidsbronnen (puur lezen, geen opslag); herinneringsregels in src/lib/herinneringen.ts (max 1 vóór/na reactiedatum, pauzeerbaar); reactiedatum is altijd een verzoek, nooit bindend — verstrijken wijzigt nooit automatisch iets.
- Activiteiten (`/activiteiten`, bell on Home) are derived in src/lib/activiteiten.ts from open proposals, audit events by others and shared Momentjes; only read-marks are stored (voorkeuren-store) and snoozing stays unavailable until a server scheduler exists — so reading never settles a request and no fake reminder exists.
